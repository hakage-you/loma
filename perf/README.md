# 性能計測

**合否は問わない。** 計測値はマシンの状態でぶれるので、CI の合否に混ぜると
落ちるだけの検査になり、「落ちたら数字を上げる」しかしなくなる。

使い方は次の2つ:

- ブランチをマージする前に、前後で回して数字を見る
- 重いと感じたときに、どこが重いのかを数字で出す

```bash
npm run perf                                   # 全部
npx playwright test --config playwright.perf.config.ts perf/startup.perf.ts
```

結果は標準出力と `perf-results/latest.json` に出る（`perf-results/` は gitignore 済み）。
部分実行しても前回の値は消えない（上書きして重ねる）。

通常の e2e（`playwright.config.ts` / `e2e/`）とはポートも設定も分けてある。

## 何を計るか

| ファイル | 見ているもの |
| --- | --- |
| `startup.perf.ts` | 起動時の IPC の回数と応答量、DOM ノード、絞り込み1回の代償 |
| `scan-refresh.perf.ts` | 解析中の1秒あたりの再取得。**解析は数時間続くので、ここの代償がそのまま積み上がる** |
| `tag-modal.perf.ts` | タグ管理の一覧・絞り込み・AI提案の描画（水増しした合成データ） |
| `real-shape.perf.ts` | **実データの形**での起動・タグ管理・絞り込み・入力 |

## 実データの形で計るには

合成データは件数を揃えられるが、偏りは作れない。実ライブラリはタグの長い裾
（使用数1回のタグが半分以上）や、1メディアあたりのタグ本数のばらつきを持っており、
これが応答量と並べ替えの重さにそのまま効く。

```bash
node tools/make-mock-fixture.mjs
```

実DB（既定 `%APPDATA%\com.hakageyou.loma\loma.db`、`LOMA_TEST_DB` で変更可）から、
**匿名化した**フィクスチャを `perf-results/fixture.json` に作る。

- ファイルパスとタグ名は捨て、連番に置き換える
- 残すのは構造だけ（件数、どのメディアがどのタグを何本持つか、分布）
- 元のDBはコピーしてから読む。**一切書き換えない**
- **コミットしない**

`real-shape.perf.ts` はこのファイルがあれば使い、無ければ丸ごと飛ばす。

> **この数字は「あるユーザーのライブラリ」のもので、標準でも理想的な分布でもない。**
> 件数そのものを期待値に固定しないこと。

## 実データに対する検証（Rust）

```bash
cd src-tauri && cargo test --lib real_db
```

`src-tauri/src/real_db.rs`。実DBの**コピー**に対して、提案の組み立てが実行ごとに
同じ結果になるかなどを見る。DB が無い環境では skip の1行を出して通る。
「コピーを書き換えても元のDBの更新時刻とサイズが変わらないこと」も検証している。
