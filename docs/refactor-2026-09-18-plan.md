## 実装した5件

### P-1. `get_media` の応答からタグ名を外した

タグの**名前を送るのをやめ、id だけ返す**ようにした。名前はフロントが
`get_all_tags` で既に持っているので、そこから引く（`src/utils/mediaTags.ts`）。

```
MediaItem.tags: TagPairItem[]   →   tag_ids: number[]
                                    basic_tag_count: number
```

当初は「タグを外して、表示中の60件ぶんだけ別コマンドで取る」案を検討していたが、
実測すると削減量はほぼ同じ（52% 対 53%）で、新しいコマンド・遅延取得・
絞り込みとの競合の始末が要る。**同じ効果なら作りが単純な方を採った。**

| | 変更前 | 変更後 |
| --- | ---: | ---: |
| `get_media` の応答 | 3.04 MB | **1.59 MB** |
| 起動時の JS ヒープ | 68.9 MB | **40.2 MB** |

**読み込み中の見た目**（いただいた回答: 「タグ型の読み込みローダーを配置し
css等で読み込みを示す」）:

タグ一覧の取得はメディア一覧と同時に走るので、メディアが先に届く瞬間がある。
そのときタグ欄を空にすると「タグが無い」と読めてしまうので、
**付いている本数ぶん、タグの形のまま読み込み中を出す**（CSS のパルス）。
タグが0件のメディア（未解析など）には出さない。

### P-3. モーダルを Esc キーで閉じられるようにした

いただいた回答（「Escで閉じられるようにするが、入力欄等変更途中状態が
あるものは閉じてよいか聞く」）のとおりにした。

- 一番手前の層だけが反応する（モーダルの上にモーダルが乗っているとき）
- IME の変換中は何もしない（Esc は変換の取り消しに使われる）
- モーダルの中に確認パネルが開いているときは、**そのパネルだけ**閉じる

「変更途中」の定義は画面ごとに決めた:

| 画面 | 何を「変更途中」とみなすか |
| --- | --- |
| メディア詳細 | タグの入力欄に文字がある |
| 詳細検索 | 開いたときから検索条件が変わっている |
| タグ管理 | タグ名を編集中 / 提案を承認済み / 統合するタグを選択済み |
| 設定 | 開いたときから設定値が変わっている、または API キーを触った |
| ログの全画面表示 | 絞り込みの入力は数えない（打ち直しが一瞬で済むため） |

### P-4. 起動時の4つの取得を同時に投げるようにした

いただいた指摘（「SQLiteの負荷ってよほどじゃないと出なそうでは？」）は
ほぼ当たっていた。記録に残っている失敗は、**データベースが遅かったのではなく、
同時に投げる本数（5本）と同時接続の上限（5）がちょうど同じだった**のが原因。

上限を 16 に上げ、`fetchMasterData` の4本を同時に投げるようにした。

| | 変更前 | 変更後 |
| --- | ---: | ---: |
| 4本を投げ終わるまでの幅（1本200ms遅延） | 605 ms | **51 ms** |

### P-5. 裏で走る取得の失敗をログファイルに残すようにした

いただいた回答（「ログに出すのはどうか」）のとおりにした。

エラー画面を出さない取得（タグ一覧・モデル一覧・解析対象外の一覧・
ログの読み出し・解析状態の確認・設定の書き込み）は `console.error` に出すだけで、
**サイドバーが空になった理由がどこにも残らなかった。**

`log_frontend_error` を Rust 側に足し、`loma.log` に
`[Frontend] <何を> — <エラー>` の形で書くようにした。
エラー画面は引き続き出さない（解析中は毎秒走るため）。

### P-7. 使われていない関数3つ — **調べ直したら全部テストが使っていた**

「消してよいか」と聞いたが、**最初の確認が不十分だった。**
本文中の呼び出しだけを見て、テストモジュール内の `use super::...` と
メソッド呼び出しを見落としていた。

| 関数 | 呼んでいる場所 |
| --- | --- |
| `rule_based_match_reason` | `commands.rs` のテスト6箇所（規則の当たり外れを1組ずつ確認） |
| `truncated` | `ollama_text.rs` のテスト3箇所 |
| `regenerate_thumbnail` | `image_io.rs` の `#[cfg(test)]` 内（透過画像の調査用） |

3つとも消さずに `#[cfg(test)]` を付けた。配布ビルドからは外れ、
`cargo check` の警告も消えた（3件 → 0件）。

## その後

### P-2. タグ一覧を「画面に映っている行だけ」にする

**2026-09-29: 今回はやらないと決まった。** 判断そのものを含めてスコープ外。

タグ管理の検索欄は `useDeferredValue`（入力の表示を優先し、一覧の作り直しを
後回しにする React の仕組み）を入れて、**1文字あたり 179ミリ秒 → 64ミリ秒
（中央値）** になった。

ただし**最悪値は約250ミリ秒のまま**。一覧が追いついたときに200行ぶんの
HTML を作り直す処理そのものの時間で、これを消すには
**リストの仮想化**（スクロール位置から「いま見えている行」を計算し、
その行だけを DOM に置く方式）への作り替えが要る。

**実装しなかった理由:**

- 「200行ずつ足していく方式」と「見えている行だけ置く方式」は作りが別で、
  混在できない。いま足していく方式は `src/hooks/useLoadMoreOnScroll.ts` を
  3箇所（タグ一覧・提案一覧・ギャラリー）で共有しているので、3箇所すべての
  作りを揃える話になる
- ライブラリを導入するか自前で書くかの判断が要る
- 250ミリ秒が実際に困っているかどうかは、使っている人にしか分からない

### P-6. 大きすぎるファイルの分割

**2026-09-29: 実装した。** 先に E2E を23件足してから分割した（詳細は報告書 §8）。

| ファイル | 行数 | E2Eテストが操作している範囲 |
| --- | ---: | --- |
| `src/components/SettingsModal.tsx` | 2,071 | 14件（画面構成・保存・プロバイダー切替・APIキー） |
| `src/components/TagManagementModal.tsx` | 1,761 | 12件（一覧・改名・手動統合・AI提案） |

**実装しなかった理由:** `SettingsModal.tsx` は E2Eテストが画面の半分しか
操作していない。概念スペクトラム検索の設定、推奨モデルのカード、
モデルのダウンロード、タグ粒度の比較は一度もクリックしていない。
この状態で分割すると、テストが操作していない側が壊れても気付けない。

順番としては「テストが操作していない部分の E2Eテストを先に書く → 分割する」。
