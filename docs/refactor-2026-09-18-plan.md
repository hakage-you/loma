# 2026-09-18 実装せず計画に留めたもの

このセッションでは「大きく仕様が変わる変更は計画のみ」という前提で作業した。
ここには**実装しなかったもの**と、その判断の根拠を書く。

数字はすべて `npm run perf` と `node tools/make-mock-fixture.mjs` の実測。
**実データは「あるユーザーのライブラリ」であって標準でも理想でもない。**

---

## P-1. `get_media` の応答からタグを外す（効果が最大）

### いま起きていること

`get_media` は絞り込みに一致した**全件**を、タグ付きで返す。

| 呼ばれる場面 | 頻度 |
| --- | --- |
| 起動時 | 1回 |
| 絞り込みを変えるたび | 毎回 |
| 解析中 | **1秒に1回** |
| タグの追加・削除・改名・統合のたび | 毎回 |

応答の内訳（実データの形・4,941件・タグ 31,849本）:

| 中身 | サイズ |
| --- | ---: |
| 全部入り | 3.32 MB |
| タグを抜く | 1.55 MB |
| タグとカテゴリを抜く | 1.44 MB |
| id / パス / 状態だけ | 0.91 MB |

**タグが 53% を占める。** 実バックエンドの応答はパスとタグ名が実物なので
さらに大きく、過去の実測では 5.20MB だった。

一方、ギャラリーは段階描画で **一度に 60件しか DOM に出さない**。
残り 4,881件ぶんのタグは、転送されてヒープに載るだけで一度も描画されない。

### 案

`get_media` からタグとカテゴリを外し、**表示中のカードぶんだけ**別のコマンドで引く。
`get_tag_sample_thumbnails(tagIds)` が既に同じ形（まとめて1往復・IN句を400件で分割）
を取っているので、それに倣う。

```
get_tags_for_media(mediaIds: Vec<i64>) -> HashMap<i64, Vec<TagPair>>
```

段階描画が 60件ずつ足していくので、1往復あたりの応答は数十KB。

### なぜ実装しなかったか

- ギャラリーのカードはタグを出すので、**取得が間に合わないカードは一瞬タグが空になる**。
  そのときに何を出すか（空・プレースホルダ・前回の値を残す）は見た目の決めごとで、
  こちらで決めるべきではない
- 絞り込みを変えた直後に前の取得が返ってくる競合の始末が要る
- 詳細モーダルとスペクトラム探索も `media` 配列のタグを読んでいる。
  そちらは「今の絞り込みに含まれないメディア」も扱うので、経路が1本増える

### 測る手順

`npm run perf` の「実データの形 / 起動」の `get_media の応答 (MB)` と
`JS ヒープ MB` を前後で比べる。

## P-2. タグ一覧の仮想化

### いま起きていること

タグ管理の絞り込み入力は、`useDeferredValue` を入れて
**1打鍵あたり 179ms → 91ms（中央値）** になった。ただし**最悪値は 298ms のまま**で、
これは「追いついたときに 200行を作り直す」代償。

| | 中央 | 最大 |
| --- | ---: | ---: |
| 1打鍵あたり | 91 ms | 298 ms |

### 案

一覧を仮想化して、画面に入っている行だけを DOM に置く。
`TAG_PAGE = 200` の段階描画を、可視範囲だけの描画に置き換える。

### なぜ実装しなかったか

- 段階描画（末尾で足す）と仮想化（可視範囲だけ置く）は**別の作りで、混ぜられない**。
  `useLoadMoreOnScroll` を使っている3箇所（タグ一覧・提案一覧・ギャラリー）の
  作りを揃える話になる
- ライブラリを足すか自前で書くかの判断が要る
- 298ms が実際に困っているのかは、使っている人にしか分からない

## P-3. モーダルを Escape で閉じる

### いま起きていること

**10個のモーダルすべてが Escape に反応しない。** 背景クリックでも閉じない
（タグ管理の画像拡大だけが背景クリックで閉じる）。

つまり**現状は不統一ではない**。一律に無い。

### なぜ実装しなかったか

「操作の統一まで実装してよい」という前提で作業したが、これは
**統一ではなく新しい挙動の追加**にあたるため、計画に留めた。

入れるなら決めることが2つある:

- 確認パネルが開いているとき（削除の確認・登録解除の確認）、Escape は
  パネルだけ閉じるのか、モーダルごと閉じるのか
- 設定モーダルは閉じても入力を保持する作りなので Escape で失うものは無いが、
  タグの編集中（`editingTagId` が立っている）はどうするか

## P-4. マスタデータの取得を並列にする

### いま起きていること

`fetchMasterData` は4つのコマンドを**逐次に await** している。

```
get_all_tags → get_parent_folders → get_scan_folders → get_settings
```

`runRefresh` も `fetchMedia` → `fetchMasterData` の順で逐次。
解析中は1秒ごとにこれが走る。

### なぜ実装しなかったか

**SQLite のプールが `max_connections(5)`。** コード中のコメントに、
進捗イベントごとに5本積み上がって
`pool timed out while waiting for an open connection` で `get_media` が
失敗した経緯が書かれている。

並列にすると、その5本を意図的に同時に使うことになる。4本に留めても、
ユーザーの操作（タグ編集など）が同じ瞬間に来ると押し出される。

**プールの上限を上げるかどうかは、DB 側の負荷の話なので判断を仰ぎたい。**

## P-5. 背景の取得の失敗を黙って捨てている

### いま起きていること

「押した操作の失敗は必ず出す」に揃えた。一方、背景の取得は出さないまま残した。

| 取得 | 失敗したとき |
| --- | --- |
| `get_media` | エラーモーダルを出す |
| `get_all_tags` / `get_parent_folders` / `get_scan_folders` / `get_settings` | **黙って捨てる**（サイドバーが空になる） |
| `get_available_models` / `get_vision_capable_models` | 黙って捨てる（意図的。コメントに理由あり） |
| `get_app_logs` | 黙って捨てる（コンソールが空になる） |

`get_media` だけモーダルを出すのは非対称。

### なぜ実装しなかったか

どちらに揃えても副作用がある。

- **出す側に揃える** → 解析中は1秒ごとに走るので、失敗が続くとモーダルが並ぶ
- **出さない側に揃える** → 一覧が取れなかったことに気付けない

「モーダルではない場所（サイドバーの見出しの横など）に小さく出す」のが
落としどころだと思うが、**どこに出すかは画面の決めごと**なので判断を仰ぎたい。

## P-6. 大きすぎるコンポーネントの分割

| ファイル | 行数 | e2e |
| --- | ---: | --- |
| `SettingsModal.tsx` | 2,022 | 14件（構成・保存・プロバイダー・APIキー） |
| `TagManagementModal.tsx` | 1,700 | 12件（一覧・改名・手動統合・AI提案） |

### なぜ実装しなかったか

`SettingsModal` は e2e が**半分の領域しか通っていない**。
埋め込み（概念スペクトラム）の節、推薦モデルのカード、ダウンロードの流れ、
タグ粒度の比較は一度も通らない。この状態で切り分けると、
通っていない側が静かに壊れても気付けない。

順番としては「通っていない領域の e2e を先に足す → 分ける」。
