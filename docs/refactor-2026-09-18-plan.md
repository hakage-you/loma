# 2026-09-18 実装せず提案に留めたもの

このセッションでは「大きく仕様が変わる変更は提案のみ」という前提で作業した。
ここには**実装しなかったもの**と、実装しなかった理由を書く。

数字はすべて `npm run perf` と `node tools/make-mock-fixture.mjs` で実際に測ったもの。
**実データは「あなたのライブラリ」の形であって、標準でも理想的な分布でもない。**

## P-1. `get_media` の応答からタグを外す（効果が最大）

### いま起きていること

`get_media` は、絞り込みに一致したメディアを**全件まとめて**返すコマンド。
1件ずつにタグの一覧が付いている。

このコマンドが呼ばれる場面:

| 場面 | 頻度 |
| --- | --- |
| アプリの起動時 | 1回 |
| サイドバーやタグで絞り込みを変えるたび | 毎回 |
| 解析の実行中 | **1秒に1回** |
| タグの追加・削除・改名・統合のたび | 毎回 |

応答のサイズ（実データの形・4,941件・タグは合計 31,849本）:

| 返す内容 | サイズ |
| --- | ---: |
| 今の中身（タグ・カテゴリを含む） | 3.32 MB |
| タグを除いた場合 | 1.55 MB |
| カテゴリも除いた場合 | 1.44 MB |
| ID・パス・解析状態だけにした場合 | 0.91 MB |

**タグが全体の 53% を占める。** 実際の Rust 側の応答はファイルパスとタグ名が
本物なのでもっと大きく、過去の計測では 5.20MB だった。

一方、ギャラリー画面は**一度に60件しか表示していない**
（スクロールすると60件ずつ増える。`src/components/GalleryGrid.tsx`）。
残り 4,881件ぶんのタグは、転送されてメモリに載るだけで一度も画面に出ない。

### 案

`get_media` からタグとカテゴリを外し、**いま画面に出している60件ぶんだけ**を
別のコマンドでまとめて取る。

```
get_tags_for_media(mediaIds: Vec<i64>) -> HashMap<i64, Vec<TagPair>>
```

同じ形の実装が既にある。`get_tag_sample_thumbnails(tagIds)` は、
複数のタグIDをまとめて1回で受け取り、SQL の `IN (...)` が受け付ける個数の上限を
避けるため400件ずつに分けて問い合わせている。これに倣えばよい。

60件ずつ増やすので、1回あたりの応答は数十KBで済む。

### 実装しなかった理由

- ギャラリーのカードはタグを表示している。**取得が間に合わないカードは
  一瞬タグ欄が空になる。** そのとき何を出すか（空のまま／灰色の枠を出す／
  前回の値を残す）は見た目の決めごとで、こちらで決めるべきではない
- 絞り込みを変えた直後に、変更前の取得結果が返ってくることがある。
  古い結果で上書きしないための処理が要る
- メディア詳細モーダルと概念スペクトラム探索も、同じメディア一覧からタグを
  読んでいる。そちらは「今の絞り込みに含まれないメディア」も扱うので、
  取得の経路が1本増える

### 効果を確かめる方法

`npm run perf` の「実データの形 / 起動」に出る
`get_media の応答 (MB)` と `JS ヒープ MB` を、変更の前後で比べる。

## P-2. タグ一覧を「画面に映っている行だけ」にする

### いま起きていること

タグ管理の検索欄は `useDeferredValue`（入力の表示を優先し、一覧の作り直しを
後回しにする React の仕組み）を入れて、
**1文字あたり 179ミリ秒 → 64ミリ秒（中央値）** になった。

ただし**最悪値は約250ミリ秒のまま**。これは一覧が追いついたときに
200行ぶんの HTML を作り直す処理そのものの時間。

| | 中央値 | 最大 |
| --- | ---: | ---: |
| 1文字打ったときの停止時間 | 64 ミリ秒 | 254 ミリ秒 |

### 案

**リストの仮想化**（画面のスクロール位置から「いま見えている行」を計算し、
その行だけを DOM に置く方式）に作り替える。
いまは「200行ずつ足していき、足したものは消さない」方式なので、
スクロールするほど DOM が増える。

### 実装しなかった理由

- 「足していく方式」と「見えている行だけ置く方式」は**作りが別で、混在できない**。
  いまこの足していく方式は `src/hooks/useLoadMoreOnScroll.ts` を使って
  3箇所（タグ一覧・提案一覧・ギャラリー）で共有しているので、
  3箇所すべての作りを揃える話になる
- ライブラリを導入するか自前で書くかの判断が要る
- 250ミリ秒が実際に困っているかどうかは、使っている人にしか分からない

## P-3. モーダルを Esc キーで閉じられるようにする

### いま起きていること

**10個あるモーダルは、すべて Esc キーに反応しない。**
背景の暗い部分をクリックしても閉じない（タグ管理の画像拡大だけが背景クリックで閉じる）。

つまり**現状はバラバラではなく、一律に無い。**

### 実装しなかった理由

「操作の統一まで実装してよい」という前提で作業したが、これは
**バラバラなものを揃えるのではなく、新しい操作を足す**ことにあたるため
提案に留めた。

入れる場合、決めることが2つある:

- 確認パネルが開いているとき（削除の確認・登録解除の確認）、Esc は
  パネルだけ閉じるのか、モーダルごと閉じるのか
- 設定モーダルは閉じても入力内容を保持する作りなので Esc で失うものは無いが、
  タグ名を編集中（鉛筆アイコンを押した状態）のときはどうするか

## P-4. 起動時の4つの取得を同時に実行する

### いま起きていること

`src/hooks/useMedia.ts` の `fetchMasterData` は、4つのコマンドを
**1つずつ順番に待って**実行している。

```
get_all_tags を呼んで待つ
  → get_parent_folders を呼んで待つ
    → get_scan_folders を呼んで待つ
      → get_settings を呼んで待つ
```

メディア一覧の取り直し（`runRefresh`）も、`fetchMedia` を待ってから
`fetchMasterData` を実行する順番になっている。解析中は1秒ごとにこれが走る。

同時に実行すれば、待ち時間は1回ぶんで済む。

### 実装しなかった理由

**SQLite への同時接続数が5に制限されている**（`src-tauri/src/db.rs` の
`max_connections(5)`）。

コード中のコメントに、進捗イベントごとに5本の問い合わせが積み上がって
`pool timed out while waiting for an open connection`（接続の空きを待って
時間切れ）というエラーで `get_media` が失敗した経緯が書かれている。

同時に実行すると、その5本の枠を意図的に一度に使うことになる。
4本に抑えたとしても、ユーザーの操作（タグ編集など）が同じ瞬間に来ると
枠が埋まって待たされる。

**同時接続数の上限を上げてよいかは、データベース側の負荷の判断なので
決めてほしい。**

## P-5. 裏で自動的に走る取得の失敗を、どこに表示するか

### いま起きていること

「ユーザーが押した操作が失敗したら必ずエラー画面を出す」に統一した。
一方、画面の裏で自動的に走っている取得は、失敗しても何も出さないまま残した。

| 取得 | 失敗したとき |
| --- | --- |
| `get_media`（メディア一覧） | エラー画面を出す |
| `get_all_tags` / `get_parent_folders` / `get_scan_folders` / `get_settings` | **何も出さない**（サイドバーが空になる） |
| `get_available_models` / `get_vision_capable_models` | 何も出さない（意図的。コードにコメントあり） |
| `get_app_logs` | 何も出さない（ログ表示が空になる） |

`get_media` だけエラー画面を出すのは揃っていない。

### 実装しなかった理由

どちらに揃えても具合が悪い。

- **出す側に揃える** → 解析中は1秒ごとに走るので、失敗が続くと
  エラー画面が次々に開く
- **出さない側に揃える** → メディア一覧が取れなかったことに気付けない

「エラー画面ではない場所（サイドバーの見出しの横に小さく出すなど）に出す」のが
落としどころだと思うが、**どこに出すかは画面の決めごと**なので判断を仰ぎたい。

## P-6. 大きすぎるファイルの分割

| ファイル | 行数 | E2Eテストが操作している範囲 |
| --- | ---: | --- |
| `src/components/SettingsModal.tsx` | 2,022 | 14件（画面構成・保存・プロバイダー切替・APIキー） |
| `src/components/TagManagementModal.tsx` | 1,700 | 12件（一覧・改名・手動統合・AI提案） |

### 実装しなかった理由

`SettingsModal.tsx` は、**E2Eテストが画面の半分しか操作していない**。
概念スペクトラム検索の設定、推奨モデルのカード、モデルのダウンロード、
タグ粒度の比較は、テストが一度もクリックしていない。

この状態でファイルを分割すると、テストが操作していない側が壊れても
気付けない。

順番としては「テストが操作していない部分の E2Eテストを先に書く → 分割する」。
