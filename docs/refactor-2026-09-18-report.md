## 2. 直したもの

### 2-1. 起動時に同じデータを何度も取っていた（軽量化）

`src/App.tsx` の `App` と `AppContent` が両方とも `useMedia()` を呼んでいた。
`useMedia` は「メディア一覧・タグ一覧の保持」「進捗イベントの購読」
「起動時のデータ取得」を全部抱えているので、2回呼ぶとそれが2組動く。

加えて `AppContent` の中で、同じデータをもう一度取る処理が2つあった。

→ 上の §0 のとおり、Context に載せて1つにまとめた。

### 2-2. 解析中にギャラリーが一度も更新されないことがあった（軽量化・安定化）

`src/hooks/useMedia.ts` は、解析の進捗イベント（`batch_progress`）を受けて
メディア一覧を取り直す。取り直しが多すぎないよう「1秒に1回まで」に抑えるつもりの
コードが入っていたが、**実際には次のように書かれていた**:

```
進捗イベントが来た
  → 前に仕掛けたタイマーを取り消す（clearTimeout）
  → 1秒後に取り直すタイマーを仕掛け直す（setTimeout）
```

この書き方だと、**進捗イベントが1秒より短い間隔で届き続ける限り、タイマーは
取り消され続けて一度も発動しない。** 結果として、解析が終わるまでギャラリーに
新しいタグが出てこない。

これに当たるのは次の場面:

- 登録フェーズ（ファイルを見つけて DB に入れる段階。5ファイルごとに進捗が飛ぶ）
- 解析が速いモデルを使っている場合

実測（メディア5,000件・進捗を200〜300ミリ秒間隔で流して10秒間）:

| | 修正前 | 修正後 |
| --- | ---: | ---: |
| `get_media` を呼んだ回数 | **0回** | 9回 |

「タイマーが仕掛かっていれば何もしない」形に変え、
**1秒に最大1回、ただし必ず実行される**ようにした。

### 2-3. タグ管理の検索欄が1文字ごとに止まっていた（軽量化）

`src/components/TagManagementModal.tsx` の「タグ名で検索...」の入力欄。
実際のライブラリ（タグ10,123件）で計測すると、**1文字打つたびに画面が
179ミリ秒（最大308ミリ秒）止まっていた。** 一覧の絞り込みと並べ替えが、
キー入力と同じタイミングでまとめて実行されていたため。

React の `useDeferredValue` を使い、「入力欄の文字は即座に表示する／
一覧の作り直しは後回しにする」形に分けた。1文字あたり **64ミリ秒（中央値）** になった。

**最悪値（約250ミリ秒）は残っている。** 一覧が追いついたときに200行を作り直す
処理そのものの時間で、これを消すには「画面に映っている行だけを DOM に置く」方式
（リストの仮想化）への作り替えが要る。これは [plan](refactor-2026-09-18-plan.md) の P-2 に回した。

### 2-4. 全画面のログ表示が 8MB を一度にメモリへ載せていた（軽量化）

`src/components/LogViewerModal.tsx`（ログの「全画面表示」ボタンで開く画面）が、
ログを読む関数を引数なしで呼んでいた。引数を省くと Rust 側の既定値
**8MB** が返る。JavaScript の文字列は1文字2バイトで持つので、
**開くたびに約16MB がメモリに載っていた。**

- 受け取る量を 2MB に制限した
- 画面に出す行数を「新しい方から2,000行まで」に制限した
- 切り捨てたことを画面に出す（`2000 行を表示（15234 行のうち新しい順）`）

### 2-5. ログファイルが無制限に大きくなっていた（安定化）

`src-tauri/src/logger.rs` はログを追記するだけで、古いものを捨てる仕組みが無かった。
実際に 5.2MB まで大きくなったものを手動で退避した形跡が残っていた
（`loma.log.bak-20260817-213102`）。

**ファイルの入れ替え**を入れた。`loma.log` が 5MB を超えたら:

```
loma.log.3 を削除
loma.log.2 → loma.log.3 に名前を変える
loma.log.1 → loma.log.2
loma.log   → loma.log.1
新しい空の loma.log を作る
```

これで合計 20MB（本体5MB + 3ファイル）で増えなくなる。

細かい配慮:

- 1行書くたびにファイルサイズを調べに行くと、解析中は毎秒書くので重くなる。
  起動時に一度だけ調べ、以降は書いたバイト数を足していく
- 入れ替えた直後は `loma.log` がほぼ空になるので、「さっきまで出ていたログが
  消えた」ように見える。読み出しは、枠が余っていれば `loma.log.1` の末尾も
  続けて読むようにした
- 「クリア」ボタンは `loma.log.1` 〜 `.3` も消す。本体だけ消すと、画面上は
  空になったのに次の読み出しで古いログが戻ってくる

### 2-6. タグ統合の提案が、実行するたびに中身の順番が変わっていた（安定化）

タグ管理の「AI提案」タブで「意味が近い」を選んだときの提案。
同じデータベース・同じアプリで2回実行すると、提案の見出しになるタグと
メンバーの並び順が入れ替わっていた（実データの742グループで発生）。

原因は `src-tauri/src/commands.rs` の `connected_components` という関数。
タグのつながりをたどるとき `HashMap` をそのまま順に読んでいた。
Rust の `HashMap` は**作るたびに内部の並び順が変わる**仕様なので、
たどり始める位置が実行ごとに変わっていた。

直したこと:

- `HashMap` から取り出したタグIDを**並べ替えてからたどる**
- 提案のメンバーを「使用数の多い順 → 名前の短い順」で並べていたが、
  **その両方が同じ値だったときの決め手が無かった**。同じ値のときは
  タグ名のアルファベット順にした（タグ名は重複しないので必ず1つに決まる）

検証は2つ置いた。**どちらも、修正を元に戻すと失敗することを確認済み。**

- `src-tauri/src/real_db.rs` — 実際のデータベースの**コピー**に対して
  提案を2回組み立て、結果が一致するか比べる。この不具合は「使用数が同じタグが
  大量にある」実データでしか出ないため、合成データでは再現できない
- `src-tauri/src/commands.rs` の単体テスト4件 — 実データが無い環境でも
  同じ誤りを検出できるようにした

### 2-7. 押した操作が失敗しても何も表示されないものが6つあった（安定化・一貫性）

失敗したときの扱いが3通りに分かれていた。

| 扱い | 件数 | 具体例 |
| --- | ---: | --- |
| 「〜に失敗しました」の見出し付きでエラー画面を出す | 5 | メディア一覧の取得、フォルダの再解析 |
| 英語の文字列でエラー画面を出す | 5 | `Could not open file: ...` |
| **`console.error` に出すだけで画面には何も出さない** | 6 | 一時停止、再開、中止、フォルダの登録解除、ログのクリア、VRAM の解放 |

3つ目は、ユーザーから見ると**ボタンを押しても何も起きない**状態。

「ユーザーが押した操作が失敗したら必ずエラー画面を出す」に統一し、
英語の文字列も日本語の文言に移した。

**ただし、画面の裏で自動的に走っている取得（タグ一覧・モデル一覧・ログの
読み出し）はエラー画面を出さないまま残した。** これらは解析中に毎秒走るので、
失敗が続くとエラー画面が次々に開いてしまう。この非対称は意図的で、
E2Eテストにも「背景の取得が失敗してもエラー画面は出さない」として書いてある。
どこに出すのが良いかは [plan](refactor-2026-09-18-plan.md) の P-5 に回した。

### 2-8. 画面ごとに英語のままだった表示（一貫性）

アプリの大半は日本語なのに、いくつかの画面だけ英語の文字列が直接書かれていた。

- **`FolderManagerModal.tsx`（登録フォルダ管理）— 画面のほぼ全部が英語。**
  `Process Pending Only` / `Re-analyze ALL Media` / `Registered Folders (2):` など。
  しかも日本語の文言ファイルには `label_add_folder` /
  `label_rescan_all` / `label_reanalyze_all` が定義済みで、**どれも使われていなかった**
- **`LogViewerModal.tsx`（ログの全画面表示）— 翻訳関数 `t()` が1箇所も無かった。**
  `Application Diagnostics & Error Logs` など
- `App.tsx` の解析制御ボタン（`Resume` / `Pause` / `Cancel`）。
  同じ列の「フォルダ追加」「同期」は日本語だった
- `LogBottomConsole.tsx`（`Recent:` など）、`SearchBar.tsx`（`+ Select` など）、
  `Sidebar.tsx`（`2 selected`）、`TagManagementModal.tsx` の通知
  （`Manual merge executed successfully!`）、`SettingsModal.tsx`、`AboutModal.tsx`

製品名 `Loma` とその説明 `Local Ollama Media Analyzer` は文言ファイルから外し、

### 2-9. フォルダの登録解除に確認が無かった（安定化・一貫性）

`src-tauri/src/commands.rs` の `remove_scan_folder` は、フォルダの登録を外すとき
**そのフォルダ配下のメディアの行・付いているタグ・サムネイル画像ファイルを
すべて削除する**（元の画像ファイル自体は消さない）。取り込み直すには
解析をやり直すことになる。

それなのに UI はゴミ箱アイコンを押した瞬間に実行していた。
**同じ画面の「全メディア再解析」には確認パネルがある**のに、より取り返しの
つかないこちらには無かった。

確認パネルを追加し、どのフォルダか（パス）と、何が消えて何が残るかを表示する。
件数は出していない。フロント側が持っているメディア一覧は**今の絞り込みの結果**
なので、そこから数えると実際より少ない数を見せることになるため。

### 2-10. 押せないボタンが理由を表示していなかった（一貫性）

解析中など、同時に実行できない操作のボタンは `disabled` になる。
`src/hooks/useExclusiveGuard.ts` のコメントには
「**`disabled` にするだけで終わらせないこと。** 理由を出さないと、ユーザーには
『ボタンが壊れた』ようにしか見えない」と書いてある。

実際には **23箇所のうち16箇所で理由を出していなかった**（マウスを乗せても
何も出ない）。すべてに理由（`解析の実行中はタグやフォルダを変更できません。…`）を
表示するようにし、`npm run check:exclusive` がこの対応を自動で確かめるようにした。

### 2-11. 同じ文字が別の意味で使われていた（一貫性）

- 削除の確認パネルの取り消しボタンが「閉じる」で、モーダルを閉じる × ボタンと
  同じ文字だった。「モーダルを閉じる＝**閉じる**／操作をやめる＝**キャンセル**」に分けた
- 登録フォルダ管理の一覧の見出しが「登録済みフォルダ」で、サイドバーの絞り込み項目と
  同じ文字だった。モーダルのタイトル（登録フォルダ管理）に合わせて
  「登録フォルダ」にした

## 3. テストの土台

### 3-1. E2Eテストが実質何も確かめていなかった

E2Eテストは `npm run dev:mock` というモードで動かす。これは Rust のバックエンドを
JavaScript の偽物（`src/mocks/core.ts`）に差し替えたブラウザ版。

**この偽物に登録が無いコマンドは、呼ばれると `undefined` を返して
`console.warn` を出すだけで、エラーにならない。** 画面は「成功した」と見なして
先に進むので、バックエンドの応答を使う処理は一度も実行されないまま
テストが成功する。

着手時、フロントが呼ぶ **22コマンド**にこの登録が無かった。
タグの改名・統合・適用、解析失敗の再試行、フォルダの再解析、モデルのダウンロードなど。
さらに、タグ統合の提案を作る3つのコマンドは `[]`（空）を返すだけで、
**「AI提案」タブの中身が一度も描画されたことがなかった**。

22コマンドぶんの偽物を実装した。実物に合わせるうえで必要だった点:

- **一括処理の終了イベントを出す。** 実物は処理の最後に
  `status: "Completed"` を送る。これが無いと画面は「解析中」のまま固まり、
  以降の操作がすべてブロックされる
- **保存と読み出しの2段構えを再現する。** 提案は「作るコマンド」が DB に保存し、
  「読み出すコマンド」が読み返す。保存を省くと、検出を実行しても提案は空のまま
- **処理が終わるまで返らないコマンドを再現する。** モデルのダウンロードは
  完了するまで返らず、呼び出し側は返ってきた時点で進捗の購読をやめる。
  偽物が即座に返すと、進捗バーが一度も描画されない

### 3-2. 追加した検査コマンド

```bash
npm run check:mock-commands
```

次の3つを突き合わせ、食い違いがあれば終了コード1で終わる（CI で落ちる）。

1. Rust 側に登録されているコマンド一覧（`src-tauri/src/lib.rs` の `invoke_handler`）
2. フロントのコードが名前を書いているコマンド
3. 偽物（`src/mocks/core.ts`）に実装があるコマンド

この検査で、Rust に登録されているがフロントのどこからも呼ばれていない
コマンド2件（`check_and_open_file` / `save_provider_api_key`）も見つかったので削除した。

### 3-3. 実データに対する Rust のテスト

`src-tauri/src/real_db.rs` を追加した。実際のデータベースの**コピー**を
一時フォルダに作って検証する。

- 元のデータベースは読むだけで、書き換えない
- コピーはテストの終わりに削除する
- データベースが見つからない環境（他人のマシン・CI）では
  `[skip] ...: 実DBが見つからないので飛ばした` と出して成功扱いにする
- 「コピーを書き換えても、元のデータベースの更新時刻とファイルサイズが
  変わらないこと」もテストで確かめている

## 4. 実データを調べて分かったこと

`node tools/make-mock-fixture.mjs` で、実際のデータベースから

### P-1 の設計を変えた理由

提案時は「タグを外して、画面に出す60件ぶんだけ別コマンドで取る」つもりだった。
実測したところ、**タグ名の代わりに id だけ返す**方式でも削減量はほぼ同じ
（52% 対 53%）だった。id 方式なら:

- 新しいコマンドが要らない
- 遅延取得と、絞り込みを変えたときの競合の始末が要らない
- タグの名前はフロントが `get_all_tags` で既に持っている

**同じ効果なら作りが単純な方**を採り、id 方式にした。

読み込み中の表示はそのまま必要だった。タグ一覧の取得はメディア一覧と同時に
走るので、メディアが先に届く瞬間がある。そのときタグ欄を空にすると
「タグが無い」と読めてしまうため、**付いている本数ぶん、タグの形のまま
読み込み中を出す**（CSS のパルス）。タグが0件のメディアには出さない。

### P-4 の指摘について

「SQLite の負荷ってよほどじゃないと出なそうでは？」はほぼ当たっていた。
記録に残っていた失敗は、**データベースが遅かったのではなく、
同時に投げる本数（5本）と同時接続の上限（5）がちょうど同じだった**のが原因。

### P-7 は私の確認不足だった

「消してよいか」と聞いたが、調べ直したら3つともテストが呼んでいた。
本文中の呼び出しだけを見て、テストモジュール内の `use super::...` と
メソッド呼び出しを見落としていた。消さずに `#[cfg(test)]` を付けている。

### データベース初期化の失敗

`.expect()` だったため、失敗すると**ウィンドウが出る前にパニックして終わり、
原因は標準エラー出力にしか出ていなかった**（配布ビルドでは誰も見られない）。

`loma.log` に次を書いてから落とすようにした:

- エラーの本文と、**原因の連鎖**（`Box<dyn Error>` は表示しても一番外側しか
  出ない。「ファイルを開けない」のような本当の原因は `source()` の先にある）
- 呼び出し履歴（`Backtrace::force_capture`。最適化ビルドでも関数名まで
  解決することを確認済み）

併せて、**データベース以外も含めたすべてのパニック**をログに残すフックを入れた。

### 対応しなかったものの理由

  渡されると `delete_password()` を呼ぶので、UI で空欄にして保存すれば消える。
  未使用の `delete_api_key` の方が不要なコード
- **指摘16（CSP が null）** — 指摘自身が書いているとおりリスクが低い
- **CI** — 入れるかどうかは判断が要るため見送り
