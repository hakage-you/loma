# VLM 連携の知見

Loma の VLM（画像解析）連携で、**コードを読んだだけでは分からない/間違えやすい**事柄をまとめる。
コード中のコメントは該当箇所にしか書けず散逸するため、背景や実測データはここに集約する。

各項目には根拠を明記する。**「実測」は計測した事実、「コード読解」はソースから導いた事実**で、
後者は未検証であることに注意すること。

検証には [`tools/prompt-check/`](../tools/prompt-check/README.md) を使う。

---

## 1. `format: "json"` は thinking 対応モデルで使ってはいけない

**根拠: 実測（2026-07-29 / `tools/prompt-check`）**

Ollama の `format: "json"` オプションを thinking 対応モデルに指定すると、**出力が破壊される**。

| モデル | thinking | 画像 | `format:"json"` | 結果 |
|---|---|---|---|---|
| `qwen3-vl:4b` | YES | あり | 無 | 正常 |
| `qwen3-vl:4b` | YES | あり | **有** | **空応答（57/57）** |
| `qwen3-vl:4b` | YES | **なし** | **有** | **空応答** |
| `qwen2:1.5b` | **NO** | なし | **有** | **正常** |

画像を外しても再現し、非 thinking モデルでは再現しない。
→ **原因はプロンプトでも画像でもなく、モデルが thinking 対応かどうか。**

壊れ方はモデル種別で異なる。

- **VLM**（`qwen3-vl:4b`）: `response` が**空文字**
- **テキストモデル**（`qwen3:14b`）: `response` が **`{}`**（構文は妥当だが中身が無い）

Loma の既定モデル（`qwen3-vl:*`, `gemma4:*`, `qwen3:14b`）は**いずれも thinking 対応**であり、全て該当する。
モデルの対応状況は `/api/tags` のレスポンスに含まれる `capabilities` に `"thinking"` があるかで判定できる。

```bash
curl -s http://localhost:11434/api/tags | jq '.models[] | {name, capabilities}'
```

JSON が壊れる問題は、`format` 指定ではなく **`parse_analysis_result`（`src-tauri/src/llm/mod.rs`）の抽出**で対処する。
同関数はコードブロックのストリップ → 最外層 `{`〜`}` の切り出し → デシリアライズを行う。

> 将来 Ollama 側で解消される可能性はある。決め打ちせず `tools/prompt-check/run.mjs --format-json both` で再確認すること。

### 過去に起きた実害

タグマージ提案の LLM 同義語検出（`src-tauri/src/commands.rs`）が `format: "json"` を指定していたため、
既定のテキストモデル `qwen3:14b` で応答が `{}` に縮退し、**LLM 由来のマージ候補が1件も追加されない状態**が続いていた。
`if let Ok(..)` の連鎖で握り潰されるため UI 上は正常に見え、マージ提案はルールベースのみに静かに縮退していた。
2026-07-29 に該当行を削除して修正済み。

**同じ欠陥が `batch.rs` にも残っていた。** 動画の「指定場面で解析」（`analyze_multi_frame_with_ollama`）は
`llm/ollama.rs` とは**別のリクエスト構造体を持つ独立した実装**で、`format: "json"` を送り続けていた。
2026-07-30 に修正。**Ollama 呼び出しの欠陥を直すときは、同種の実装が他に無いか必ず探すこと。**
本流だけ直しても、複製側は静かに壊れたまま残る。

## 2. `done_reason` は失敗を検知できないことがある

**根拠: 実測（2026-07-29）**

上記の `format:"json"` 起因の空応答は、**`done_reason` が `"length"` ではなく `"stop"`（正常終了）で返る**。

`src-tauri/src/llm/ollama.rs` の `analyze_with_ctx_escalation` は
**`done_reason == "length"` かつ応答が空**のときにだけ `num_ctx` を倍増して再試行する。
そのため上記の失敗は**ガードをすり抜けて静かに抜ける**。

**空応答を検知したいなら `done_reason` ではなく `response` の中身を見ること。**

## 3. `LIGHT` プロンプトはタグ本数を指示していなかった

**根拠: 実測（2026-07-29 / `qwen3-vl:4b` / 19枚 × 3回 = 57試行）**

`VLM_ANALYSIS_PROMPT_LIGHT` は「軽量・小型モデル向けの高速・**安定化**プロンプト」で、
**極小であること自体が設計意図**である。しかし本数指示が無く、例示もタグ1個だけだったため、
VLM が例示に引きずられて極端に少ないタグしか返さなかった。

| 条件 | パース失敗 | 空文字 | **タグ<3** | タグ数 中央値 | min/max | 秒（中央値） |
|---|---|---|---|---|---|---|
| 本数指示なし（改修前） | 0% | 0% | **82%** | 2 | 0/4 | 18.5 |
| `Output 3 to 5 tags.` | 0% | 0% | 0% | 3 | 3/5 | 13.3 |
| **同 + `en`/`ja` 必須（採用）** | 0% | 0% | 0% | 3 | 3/5 | 14.3 |

- 改修前は**単色・グラデーションなどの低情報量画像で 100% がタグ3個未満**。
  `{"categories":["other"],"tags":[]}` という**タグ0個**の正常応答も返る（パース成功扱いになる）。
- **指示を足しても安定性は劣化せず、むしろ速くなった。** 「何個出すか」の判断に費やされていた推論が減ったためと推測される。
- **低情報量画像でもタグの捏造は起きなかった。** 単色グレー → `screen / gray / blank`、
  グラデーション → `gradient / background / monochrome` と実態に即した記述で埋めていた。
  ただし**汎用語に寄る**（`background` `graphic` `abstract` は DETAILED が明示的に禁止している語群。LIGHT には禁止規則が無い）。

### `en`/`ja` 必須の明示に効果があった

本数指示のみの案と、`Each tag MUST have both "en" and "ja".` を足した案では、
**タグ本数・パース失敗率・速度はすべて同点**だったが、以下2つの独立した指標で後者が優れていた。

| 指標 | 本数のみ | **+ en/ja 必須** |
|---|---|---|
| 反復間のタグ一致度（Jaccard / 同一画像3回） | 0.399 | **0.549**（19枚中12枚で優位） |
| 同じ57試行で生成されたユニークタグ数 | 105 | **89**（15%少ない） |

**語彙が少ないことは実利がある** — タグマージの負担が減り、各タグの出現頻度が上がって統計が安定する。

## 4. thinking モデルは推論トークンを大量に消費する

**根拠: 実測（2026-07-29）**

`qwen3-vl:4b` の `thinking` フィールドの文字数（LIGHT プロンプト時）:

- 平均 **6,521文字** / 最大 **18,645文字**
- **単色グレー1枚に対して 9,421文字**、グラデーション1枚に対して 4,412文字

真っ白な画像にも延々と推論する。`num_ctx` の設計（`recommended_num_ctx`）が
粒度に応じて 8192〜16384 と大きめなのはこのため。

### だから `num_predict` を指定してはいけない

**根拠: 実測（2026-07-30 / `qwen3-vl:4b` / サムネイル3枚 / 4試行）**

`num_predict` は生成トークンの上限だが、**thinking の消費分も同じ枠から引かれる。**
上限に達すると thinking の途中で打ち切られ、**答えを書く前に終わる**。

| オプション | 空応答 | `done_reason` | `eval_count` |
|---|---|---|---|
| `num_predict: 2048` | **3/4** | length | ちょうど 2048 で停止 |
| 無指定 | 0/4 | stop | 2,148〜4,337（ばらつく） |

動画マルチフレーム解析（`batch.rs`）が `num_predict: 2048` を指定していたため、
**「指定場面で解析」が既定モデルで高確率に失敗していた**（2026-07-30 修正）。
`format: "json"` を外しただけでは直らず、この2つは独立した欠陥だった。

**上限を上げるのではなく無指定にする。** 必要量はモデルと画像枚数で変わるため、
固定値を置き直しても同じ壊れ方を再現するだけになる。実測では画像3枚で
thinking が 7,600〜15,300 文字に達し、試行ごとに 2 倍近く振れた。

再現手順:

```bash
# 修正前の設定（空応答になる）
node tools/prompt-check/run.mjs --frames 3 --sample 3 --repeat 2 --num-predict 2048

# 現行の設定（batch.rs から実値を抽出して流す）
node tools/prompt-check/run.mjs --frames 3 --sample 3 --repeat 2
```

## 5. プロンプト種別はモデル名のパラメータ数で決まる

**根拠: コード読解（`src-tauri/src/llm/mod.rs` の `get_vlm_prompt_info`）**

1. 外部プロバイダ（Gemini / OpenAI / Claude）→ 常に **DETAILED**
2. モデル名からパラメータ数をパースできる場合、**10B 以上なら DETAILED、未満なら LIGHT**
3. パース失敗時、名前に `large` / `giant` / `pro` を含めば DETAILED、それ以外は **LIGHT に安全フォールバック**

つまり `qwen3-vl:8b` は LIGHT、`gemma4:12b` は DETAILED になる。
**解析に使ったプロンプト種別・モデル・粒度は `media` テーブルに記録されない**ため、
既存メディアがどちらで解析されたかを後から特定する手段は無い（`tag_kind` から間接的に推測するしかない）。

## 6. タグの英語名は正規化で語が壊れることがある

**根拠: コード読解（`src-tauri/src/batch.rs` の `normalize_tag_en`）／未実測**

同関数は機械的な単数形化を行うため、以下のような語を壊す。

| 入力 | 保存される `name` |
|---|---|
| `lens` | `len` |
| `canvas` | `canva` |
| `virus` | `viru` |
| `cactus` | `cactu` |
| `series` | `sery` |
| `glasses` | `glasse` |

一方 **`name_ja` は `trim()` のみで無加工保存**される。
タグ名を意味的に扱う処理（埋め込み生成など）では、**英語名ではなく `name_ja` を使うほうが安全**。

## 7. Rust は文字列リテラル内の CRLF を LF に正規化する

**根拠: 実測（`tools/prompt-check` 構築時にハマった）**

`src-tauri/src/llm/mod.rs` は CRLF で保存されているが、
**Rust は文字列リテラル（生文字列リテラル `r#"..."#` を含む）内の CRLF を LF に正規化する**。
そのため実行時のプロンプトは LF のみになる。

外部ツールから `mod.rs` を読んでプロンプトを再現する場合、**同じ正規化をしないと本番と1バイト単位で異なる**。
実際 `build_detailed_with_descriptive` が探すマーカー `"\n\n# Output Format\n"` は、
CRLF を残したままだと一致しない。

## 8. プロンプトを改修したときの確認手順

**プロンプトは「良くしたつもり」で壊れる。** 改修のたびに [`tools/prompt-check/`](../tools/prompt-check/README.md) を回す。

```bash
# 改修前後を同じ画像で比較
node tools/prompt-check/run.mjs --variants light,light_count_schema --repeat 3 --sample 12
```

**必ず3つを別軸で見る。** タグ本数が改善しても、他が悪化していれば採用しない。

| 軸 | 見落とすと何が起きるか |
|---|---|
| タグ本数の分布 | タグ数不足でメディアが機能から除外される |
| JSON パース失敗率 | 解析が丸ごと失敗する |
| 空文字応答率 | `format:"json"` の可否がここに出る |

**低情報量画像（単色・グラデーション・空白UI風）を必ず含めること。** 下限は実写だけを測っても観測できない。
ハーネスが自動生成するので、追加の準備は不要。

パース判定は `AnalysisResult` と同じ厳格さで行う必要がある
（`categories` / `tags` 必須、各タグに `en` / `ja` 必須。`"tags": ["cat"]` のような文字列配列は構文が正しくても失敗扱い）。
