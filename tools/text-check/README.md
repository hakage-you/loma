# テキストモデル比較ハーネス（タグ同義語検出）

`RECOMMENDED_TEXT_MODELS`（タグ整理用モデル）の実際の用途を測るためのツール。

`src-tauri/src/commands.rs` の `run_suggest_tag_merges_logic` を確認したところ、
`ollama_text_model` が使われているのは**「タグ一覧 → 同義語ペアをJSONで返す」単一タスクのみ**
だった。翻訳用途の呼び出しは存在しない（日本語訳自体は VLM 側のプロンプトで生成されている）。
このツールはその1機能だけを測る（画像を扱う `tools/prompt-check` とは対象が異なる）。

> **重要: 本番ではこの機能はほぼ動かない。** LLM 分岐は `free_tags.len() <= 300` の
> 中にあり、301件以上のライブラリでは丸ごとスキップされる（実測: 5,827タグのライブラリで
> 一度も実行されていない）。**上限の是非を決めるまで、ここでのモデル選定は結論を出せない。**
>
> **さらに本番の Ollama 呼び出しには `options` が無い**（`commands.rs`）。
> num_ctx は Ollama 既定（通常4096）なので、大きなプロンプトは**黙って切り捨てられる**。
> 切られるのは先頭＝指示文側で、`done_reason` は `stop` で返る。
> `format:"json"` が `{}` に縮退した事故と同じ形の静かな故障なので、
> **大きな入力を測るときは `prompt_eval_count` を必ず記録して切り捨てを検出すること。**

## まず現行を測る（`baseline.mjs`）

**新方式を評価する前に、現行との対照を取る。** ベースライン無しでは
「新方式の提案は良いか」は言えても**「今より良いか」に答えられない**。

```bash
node tools/text-check/baseline.mjs          # スナップショットから現行提案を全件生成
node tools/text-check/baseline.mjs --reuse  # スナップショットを作り直さない
```

タグが301件以上あると本番の LLM ブロックはスキップされるので、
`run_suggest_tag_merges_logic` をそのまま呼べば**純粋なルールベースの結果**が得られる。

実測（2026-08-01 / 5,827タグ）:

| 指標 | 値 |
|---|---|
| 提案数 | 365 |
| 延べメンバー数 | 1,071 |
| 2件のみの提案 | 209（57%） |

**「似たグループが散発的に数百件出る」問題は現行で既に起きている。**
質も低い（`star`(星) に `stair`/`staircase`(階段) が混ざる、
`gate` に `game`/`crane`/`texture` が入る等）。**超えるべき水準は低いが、
これらを再生産しないことは要求に含まれる。**

## 階層の事前分布（`hierarchy-scan.mjs`）

```bash
node tools/text-check/hierarchy-scan.mjs
```

「LLM が階層提案を出したか」だけを見ても解釈できない。0件だったとき、
プロンプトが効いていないのか・そもそも親タグが存在しないのかを区別できないため。
**事前分布を先に押さえてから提案数を読む。**

`animal`/`cat`/`dog` を階層の例に使っていたが、**`animal` はカテゴリタグ
（`is_category=1`）で本番の入力に入らない**と判明した。本番で永久に成立しない例を
設計根拠にしていたことになる。実在するのは `container`⊃`bowl`⊃`soup_bowl` など。

**`target` の使用数逆転に注意。** シード16組のうち13組（81%）で親のほうが使用数が少ない
（`vehicle`(1件) が `car`(20件) を吸収する形）。
「最も一般的」と「よく使われている」は系統的に食い違う。

## 何を測るか

`tools/prompt-check` と同じ4軸:

| 軸 | 出どころ | 落とし穴 |
|---|---|---|
| **同義語ペアの妥当性** | 有効ペアの目視（下記） | **正解セットが要る。** ランダム抽出＋目視では測れない |
| **JSONパース失敗率 / 空文字応答率** | レスポンスのパース結果 | `format:"json"` が thinking モデルの応答を `{}` に縮退させる既知の欠陥がここに出る |
| **速度** | `eval_count` / `eval_duration` | 壁時計だけだとロード時間に引きずられる |
| **VRAM** | `/api/ps` の `size_vram` | 他のモデルが常駐していると混ざる |

## 設計上の約束

**プロンプト文面を JS 側にミラーしない。** `prompt.mjs` は `commands.rs` の
`build_synonym_prompt` を `cargo test get_synonym_prompt -- --ignored` 経由で呼び、
本番と同じ文面を取得する（`tools/prompt-check` が `mod.rs` からプロンプトを抽出しているのと
同じ理由。ここは `const` ではなく関数なので、正規表現抽出ではなく cargo test 経由で呼ぶ）。

**入力タグは実ライブラリから取る。** `tools/embedding-check/snapshot.mjs` と同じ手法
（`VACUUM INTO` で WAL を反映した readonly スナップショット）を使い回す。

**本番の呼び出し条件を踏襲する。** `run_suggest_tag_merges_logic` は `free_tags.len()` が
2〜300 件のときだけ LLM を呼ぶ。`--sizes` はこのレンジを跨いだ複数パターンで比較する
（既定 `10,50,200`）。

**`format:"json"` は既定で送らない。** 本番も送っていない（`format:"json"` が thinking
モデルの応答を `{}` に縮退させる既知の欠陥があるため）。`--format-json both` で
将来の Ollama 側の改善を実測で確認できる。

## 使い方

```bash
# 1モデルを計測（回帰確認）
node tools/text-check/run.mjs --models qwen3:14b

# モデルを比較する
node tools/text-check/run.mjs --models qwen2.5:3b,qwen2.5:7b,qwen3:14b --sizes 10,50,200 --repeat 3

# format:"json" の on/off を比較する
node tools/text-check/run.mjs --models qwen3:14b --format-json both

# スナップショットを使い回す（DBの更新は反映されない）
node tools/text-check/run.mjs --models qwen3:14b --reuse
```

| オプション | 既定 | 説明 |
|---|---|---|
| `--models` | `qwen3:14b` | 比較するモデル（カンマ区切りでモデル横断比較） |
| `--sizes` | `10,50,200` | 入力するタグ件数（本番の呼び出し条件 2〜300 を跨ぐ） |
| `--repeat` | `2` | 同一条件あたりの試行回数 |
| `--format-json` | `off` | `off` / `on` / `both` |
| `--db` | アプリの app_data_dir | 対象DB。省略時は `tauri.conf.json` の identifier から解決する |
| `--url` | `http://localhost:11434` | Ollama のエンドポイント |
| `--reuse` | off | スナップショットを使い回す |
| `--side-by-side-size` | `--sizes` の先頭値 | 横並び目視表示に使うサイズ |
| `--no-html` | — | HTML レポートを出さない |

結果は `results/` に JSON + 同名 HTML で残る（gitignore 済み）。
`node tools/text-check/report.mjs [<results.json>]` で見せ方だけ作り直せる
（計測はやり直さない。`tools/prompt-check/report.mjs` と同じ方針）。

## 分割の可否（`partition-check.mjs`）— GPU 不要

**先に読むこと。** 「1プロンプトに入らないなら分割すればよい」は成立しない。
埋め込みの粗分割が包括関係を同居させられるかを測ると:

| 対象プール | 上限100での同居率（ルール到達分を除く） | ランダム |
|---|---|---|
| basic 全2,287件 | 19% | 3.1% |
| 単語1語 1,094件 | 17% | 6.5% |

対照実験（cos ≥ 0.90 の124ペア）は**96%保存される**ので分割の実装は健全。
低い値は**埋め込みが包括関係を持っていないという性質そのもの**。
`container` ⊃ bowl/cup/plate/glass と `structure` ⊃ `greenhouse` は全上限で分かれる。

```bash
node tools/text-check/partition-check.mjs --db tools/embedding-check/results/snapshot-bge-m3.db --model bge-m3
node tools/text-check/partition-check.mjs --words single --caps 60,100,150,200,300   # Pass H 用
```

**区画の仕事は同居させること（再現率）だけ。** 統合すべきでない組が同居しても
失敗ではない（棄却は区画の中で LLM がやる）。よって `WANT_APART` は合否に数えない。
**ランダム同居率を必ず併記する** — 上限300なら区画は8個前後で、でたらめでも12%は同居する。

## S1: 実行可能性ラダー（`ladder.mjs`）

**「go/no-go 判定」ではない。** 測っているのは「切り捨てられずに1往復が完了するか」
だけで、これは必要条件でしかない。**合格はシード回収率で決める。**

```bash
node tools/text-check/ladder.mjs --model qwen3:14b --sizes 100,200,300 --words single
node tools/text-check/ladder.mjs --model qwen3:14b --sizes 100 --no-pin-seeds   # 実運用の再現
```

| オプション | 既定 | 説明 |
|---|---|---|
| `--model` | `qwen3:14b` | 1本に固定して測る（モデル比較は S4） |
| `--num-ctx` | `32768` | **本番に無い条件**。本番は `options` を送っていない |
| `--sizes` | `100,300,600,1200,2287` | 入力件数のラダー |
| `--kind` | `basic` | `basic` / `descriptive` |
| `--words` | `all` | `single` で単語1語のみ（**包括関係の14/18がここに閉じる**） |
| `--think` | `auto` | `on` / `off`。**切ると全軸で悪化する**（下記） |
| `--timeout` | `900` | 1回の生成に許す秒数。**これが唯一の歯止め**（下記） |
| `--variant` | `group_jsonl` | `candidates.mjs` の候補プロンプト |
| `--ja` | `on` | `name (name_ja)` を付けるか。`both` で両方 |
| `--no-pin-seeds` | — | シード固定を外す。**実運用に近いのはこちら** |

### シード回収率が合格条件

「切り捨てゼロ・パース成功」だけを見ると、**安全に3グループだけ出すモデルが
最高得点になる**。手で実在を確認した階層シードを入力に固定し、
**そのうち何組を実際に拾ったか**を数える。埋め込みで作った正解セットと違い自己採点にならない。

シード固定は件数を変えず非シード側を削り、**元の並び順に戻す**
（先頭に固めるとシードだけが最良の位置に来て回収率が水増しされる）。

> **シード固定ありは実運用ではない。** 親と子が同じチャンクに入ることが保証されるため。
> 実測: 同じ n=100 で固定ありは8グループ（`container <- bowl, plate, glass, cup` 等）、
> **固定なしは3グループ**（2件ペアばかり）。
> **価値のある包括提案が大きいグループになるのは親と複数の子が同居しているから。**

### thinking を切ってはいけない（qwen3:14b / n=100）

| think | 所要 | eval | 有効group | 不正行 | シード回収 |
|---|---|---|---|---|---|
| on | **98秒** | 4,142 | 8/8 | 0 | **13/14** |
| off | 320秒 | 19,512 | 20/24 | 8/32 | 10/14 |

**thinking が出力を短く正確に保っている。** 切ると3倍遅く生成量4.7倍。

### 生成長は Ollama では止められない

`num_ctx` は**文脈が埋まるとシフトして生成が続く**ので上限にならない
（`num_ctx 8192` に対して `eval_count 19,512` の実測）。`num_predict` は thinking を壊す。
**`--timeout` が唯一の歯止め。** 無いと発散1回につき1時間半が溶ける
（qwen3:14b は n=200 で98分・32万トークン生成して空応答を返した）。

### 切り捨てを検出できないと計測が全部無意味になる

トークナイザを持たないので絶対値では判定できない。代わりに
**入力文字数あたりの `prompt_eval_count`（トークン密度）が急落した段**を切り捨てとみなす
（num_ctx に張り付いた場合も同様）。**切り捨てが起きた回の品質評価は破棄する。**
指示文を失ったモデルの出力を「プロンプトが悪い」と読んではいけない。

### 失敗は分けて数える

分けないとどれを直せばいいのか分からない。

| 分類 | 意味 |
|---|---|
| **環境障害** | Ollama の `llama-server` 落ち（既知 issue）。**モデルの失敗ではない**。再起動して測り直す |
| **時間切れ** | `--timeout` 超過。「この規模では終わらない」という測定値 |
| 文脈長で落ちた | 切り捨て検出。品質評価は破棄 |
| 出力が切れた | `done_reason == "length"` で答えの途中 |
| **生成が発散した** | `done_reason == "length"` だが**答えを出さずに生成し続けた**。下記 |
| パースできない | スキーマ違反・空応答 |
| **パースは通ったが有効グループ0** | 見落としやすい。下記 |

> **「途中で切れた」と「発散した」は別物。** どちらも `done_reason == "length"` で返るが、
> 診断も対策も違う。実測: qwen3:14b は n=200 で `eval_count = 327,680`
> （`num_ctx` のちょうど10倍）を吐き、応答は空だった。**プロンプトを短くしても直らない。
> この規模がこのモデルの限界という意味。**

最後のものは「成功」に見えるが実質失敗。内訳をさらに
**例のコピー / 発明タグ / 実質1件以下 / 種別またぎ**に分ける。

> **実測で見つかった failure mode: プロンプトの例をそのまま返す。**
> `qwen2:1.5b` は入力タグを一切見ず
> `{"target":"container","members":["bowl","cup","soup_bowl","rice_bowl"]}` を返した。
> これは私がプロンプトに書いた階層の例そのもの。「入力に無いタグを発明した」のとは
> 診断が違う（プロンプトの例が強すぎる）ので、`EXAMPLE_TAG_NAMES` と突き合わせて分けて数える。

### JSONL で出させる理由

1個の巨大な JSON だと、出力が途中で切れたときに**全部失われて「パース失敗1件」としか
記録できない**。1グループ1行なら (a) 直前まで使える、(b) 失敗が二値でなく率になる、
(c) 原因を行単位で特定できる。実測でも、途中で切れた応答から単一JSONは0グループ、
JSONL は2グループを回収できた。

## 段1: 包括語の抽出（`parent-scan.mjs`）

**分割できない問題を、分割できる問題に置き換える道具。**

グルーピングは O(n²) の突き合わせなので分割できない（分けると親と子が別チャンクに落ち、
埋め込みで寄せても17〜25%しか同居しない）。一方**「このタグは包括語か」の判定は
タグ単位で独立**なので任意に分割してよい。段1で包括語 P 件を確定し、
段2では **P 件を全チャンクに注入する**。これで親子の同居が構造的に保証される。

```bash
node tools/text-check/parent-scan.mjs --model qwen3:14b --top 5 --think off
```

| オプション | 既定 | 説明 |
|---|---|---|
| `--chunk` | `100` | 1回に判定させる件数 |
| `--top` | `0` | **1チャンクから選ばせる件数。0 は絶対判断（非推奨・下記）** |
| `--think` | `auto` | 段1は出力が短いので `off` が速い |
| `--timeout` | `600` | 1回の生成に許す秒数 |
| `--limit` | `0` | 試運転用。先頭N件だけ対象にする |

### 絶対判断は閾値が振れる。相対判断に変えること

「包括語か否か」を聞くと、**同じプロンプト・同じ入力でモデルの閾値が大きく振れる**:

| 判定方式 | think | 1チャンクの所要 | 抽出率 | P（1,094件） |
|---|---|---|---|---|
| 絶対（`--top 0`） | on | 262秒 / 600秒タイムアウト | 4% | ≈44 |
| 絶対（`--top 0`） | off | 45秒 / 17秒 | 52% | ≈570 |
| **相対（`--top 5`）** | off | **7〜8秒** | **正確に5%** | **55** |

P は段2の実行可能性を直接決める（P≈570 では包括語だけで1回分の枠を使い切る）。
**LLM は閾値判断より順位付けの方が安定し、しかも P を直接制御できる。**
出力長も N 行に有界になるので発散の余地が減る。

### 見落とした親はその下の階層が永久に出ない

段1で落とした包括語は段2でも絶対に出てこない。
`HIERARCHY_SEEDS` の親（container / bowl / footwear / vehicle / structure / furniture）を
拾えているかを毎回検証する。**これは非循環の再現率**で、埋め込みで作った正解セットと違い
自己採点にならない。

## 段2: カテゴリへの割り当てと集約（`assign-scan.mjs`）

**設計の核心。** 段1のカテゴリを全チャンクに入れ、残りのタグを割り当て、
**チャンクを跨いで target ごとに集約する。**

```bash
node tools/text-check/assign-scan.mjs --model qwen3:14b --chunk 50 \
  --parents results/parent-scan-A.json,results/parent-scan-B.json
```

| オプション | 既定 | 説明 |
|---|---|---|
| `--parents` | 必須 | `parent-scan` の結果 JSON（カンマ区切りで和集合） |
| `--chunk` | `50` | 1回に割り当てさせる対象タグ数 |
| `--retry-empty` | `2` | **割当0・時間切れの再試行回数**（下記） |
| `--timeout` | `600` | 1回の生成に許す秒数 |
| `--max-chunks` | `0` | 試運転用。先頭Nチャンクだけ |

### 「グルーピング」ではなく「割り当て」にする理由

段1のカテゴリをそのまま混ぜてグルーピングさせると、モデルは**毎回カテゴリどうしの
関係まで解き直す**（`container`/`utensil`/`tableware`、`structure`/`building`/`room`）。
実測: カテゴリ75件＋通常25件で600秒タイムアウト、48件＋52件でも900秒タイムアウト。
**P に関わらず成立しない。**

カテゴリ間の関係は一度決めれば済むので、段2は割り当てだけに制約する。

### 大きいグループは「同居」ではなく「集約」で作る

素の分割では親と子が同じチャンクに落ちないと大きい提案が出ず、
埋め込みで寄せても17〜25%しか同居しない。集約すればこの確率に依存しなくなる:

```
チャンク1  → container <- bowl, plate, cup, bottle, tray
チャンク9  → container <- pot, teapot, bucket, jar
チャンク14 → container <- crate, basket, trough, pitcher, barrel
──────────────────────────────────────────────────
集約       → container <- 上記14件
```

| | 大きいグループができる条件 | 実測 |
|---|---|---|
| 分割してグルーピング | 親と子が同じチャンクに同居 | 3グループ（うち1件はルールが拾う組） |
| **割り当て＋集約** | 子がどこかのチャンクに居ればよい | 54グループ・最大57件・3件以上が44 |

### 0件と時間切れは必ず再試行する

**同一プロンプト・同一入力・temperature 0.1 でも結果が振れる。**
21チャンク中3つが割当0を返し（`done_reason` は `stop`、`eval_count` も3,000前後）、
うち1つを単独で再実行すると **0件 → 78件**。消えたチャンクには
`bowl`/`cup`/`plate`/`glass`/`car` という最も使用数の多いタグが含まれていた。

**時間切れも同じ扱いにする。** ただし同条件では再び時間切れになるので、
**thinking を切って条件を変える**（実測: 400秒で時間切れ → think off で68件回収）。
どのチャンクが詰まるかも実行ごとに変わるので、個別対処ではなく仕組みで拾う。

> **根拠は非対称性。** 誤った提案は見えるし除外も安い（UI はメンバー単位の除外に対応）。
> **出なかった提案は見えないし取り返せない。** 追加の呼び出しの方が安い。

### シード回収率を単独で読まない

## 品質の判定 — 正解セットが無いと測れない

**「実タグをランダムに抜いて出力を目視」という評価をしてはいけない。**
2026-08-01 にこれをやって結論が出せず、やり直しになった。理由は3つある。

1. **正解が無いと再現率が原理的に測れない。** モデルが 0 件返したとき、
   「正しく黙った」のか「見逃した」のか区別できない
2. **5,800タグから10件抜くと、真の同義語ペアが入る確率はほぼゼロ。**
   大半のサンプルは正解が「0件」であり、実際には*たくさん返すモデルほど悪い*。
   にもかかわらず「ペア数中央値」を能力の指標に並べてしまい、評価が逆立ちしていた
3. **ルールベースが既に拾うペアを加点してしまう。** 本番は LLM の前にルール判定
   （同一日本語表記／単数形正規化／共通キーフレーズ／日本語共通プレフィックス／編集距離）を
   通す。**LLM の価値はルールで到達できないペアだけ。**
   実測では類似度上位 400 ペアのうち **345 件（86%）がルールで拾える**ので、
   ここを分けないと LLM の貢献をまるごと過大評価する

### 自己対応を有効ペアと数えない

モデルは「1つのタグの英語名と日本語訳」を並べただけのペアを大量に返す
（`apple` = `りんご` など）。本番は `find_tag` が両方を同じタグに解決し
`t1.id != t2.id` で弾くので実害は無いが、**生成数だけ見ると質を大幅に過大評価する。**

`run.mjs` は本番と同じ `find_tag` + `id`/`kind` フィルタを通した後の数を
**有効ペア**として集計し、自己対応率も併記する。実測では `qwen2.5:7b` の
生成ペアの **92%** が自己対応だった。

### 正解セットの作り方（`gold-set.mjs`）

総当りで人にラベル付けさせる代わりに、既存のタグ埋め込みで候補を絞る。

```bash
node tools/text-check/gold-set.mjs --db tools/embedding-check/results/snapshot-bge-m3.db --model bge-m3 --top 400
```

1. 同一種別内でコサイン類似度の高いペアを上位 N 件取る
2. **ルールベース判定が既に拾うペアを落とす**（`commands.rs` の `rule_based_match_reason` を
   `cargo test classify_rule_pairs` 経由で呼ぶ。JS にミラーを持たない）
3. 残りを `results/gold-set-candidates.tsv` に書き出す

`label` 列に `y`（統合すべき同義語）/ `n`（似ているが統合すべきでない）を入れる。
**`n` を捨てないこと。** 誤マージはユーザーのデータを壊すので、適合率の評価には
「似ているが違う」ハードネガティブが要る（例: `watch`(腕時計) と `clock`(時計)、
`road_sign`(道路標識) と `street_marking`(道路標示)）。

ラベル付けが済んだら、正解ペアを混ぜたサンプルを作って再現率を測る
（この経路は正解セットが揃ってから実装する）。
