# 埋め込みモデル比較ハーネス

概念スペクトラム検索（「似ているメディアを探す」）のタグ埋め込みについて、
**モデルを変えたときに何がどう変わるか**を実データで測るためのツール。

埋め込みモデルは**名前・次元数・パラメータ数から良し悪しを判断できない**。
実際に自分のライブラリで類似度分布を測るまで、使い物になるかどうか分からない。
実測例（2026-07-30 / 同一ライブラリ 1,008件）: 類似度の sd は
`bge-m3` が 0.132、`qwen3-embedding:8b` が 0.198 で **1.5 倍の開き**があった。

## 何を測るか

| スクリプト | 測るもの | Ollama |
|---|---|---|
| `db-stats.mjs` | ライブラリの素性（タグ本数分布・descriptive 保有率・保存量） | 不要 |
| `run.mjs` | 類似度分布・ハブ化・群分離・所要時間・上位/中位/下位の実例 | **必要** |

**まず `db-stats.mjs` を走らせること。** 母集団を知らずに類似度の数値を読むと解釈を誤る。
2026-07-30 の計測では「descriptive 保有群と非保有群の分離度」を測ろうとしたが、
実際には全メディアが descriptive を保有していて**対照群が存在せず、指標は最初から意味を持ち得なかった**。
`db-stats.mjs` はこれを最初に警告する。

## 使い方

```bash
# 1. ライブラリの素性を見る（稼働中のDBから安全に読む）
node tools/embedding-check/db-stats.mjs

# 2. モデルを比較する（未生成タグのベクトル化から実行される）
node tools/embedding-check/run.mjs --models bge-m3,qwen3-embedding:8b

# 実例だけ見たい / 分布だけ見たい
node tools/embedding-check/run.mjs --models bge-m3 --only examples --verbose
```

| オプション | 既定 | 説明 |
|---|---|---|
| `--models` | `bge-m3` | 比較するモデル（カンマ区切り）。Ollama に導入済みであること |
| `--db` | アプリの app_data_dir | 対象DB。省略時は `tauri.conf.json` の identifier から解決する |
| `--url` | `http://localhost:11434` | Ollama のエンドポイント |
| `--only` | `both` | `dist`（分布）/ `examples`（実例）/ `both` |
| `--reuse` | off | スナップショットと生成済みベクトルを使い回す。**DBの更新は反映されない** |
| `--verbose` | off | `--only examples` でも実例を標準出力に出す |

結果は `results/` に残る（gitignore 済み）。

ベクトル生成は 5,500 タグで 2〜3 分かかる。出力の見せ方を調整するなど、
**DBが変わっていないと分かっている**反復では `--reuse` を付けると省ける。

## 設計上の約束

**計測ロジックを JS 側に持たない。** `run.mjs` が呼ぶのは
`src-tauri/src/embedding.rs` の `#[ignore]` テスト2本で、その中で走るのは
**本番と同じ `build_library` / `compute_diagnostics`** である。
ここで重心計算やコサイン類似度を再実装すると、
「テストは通るが本番と違うものを測っていた」という最悪の失敗をする
（`tools/prompt-check` がプロンプト本文を `mod.rs` から抽出しているのと同じ理由）。

**稼働中のDBを単純コピーしてはいけない。** Loma は WAL モードで動く
（`src-tauri/src/db.rs` の `PRAGMA journal_mode = WAL`）。`loma.db` だけをコピーすると
`loma.db-wal` に残っている直近の書き込みを取りこぼす。
2026-07-30 に実際にこれをやり、削除済みのメディア2件とタグ18件を含む古い状態を計測した。
`snapshot.mjs` は `VACUUM INTO` で WAL を反映した一貫スナップショットを作る。

**スナップショットは readonly で開く。** 書き込み可で開いて close すると
SQLite が WAL をチェックポイントし、**計測ツールがユーザーのDBを書き換える**。
データは失われないが、計測対象を計測が動かすことになる。

**モデルごとに別スナップショットを使う。** 使い回すと先のモデルのベクトルが
`tag_embeddings` に残り、保存量が混ざるうえ「未生成タグ0件」で生成時間が測れなくなる。

## 結果の読み方

### 分布（`measure_real_library`）

`centering` ON / OFF × `descriptive` ON / OFF の4条件を出す。

| 指標 | 見方 |
|---|---|
| **sd / レンジ幅** | **大きいほど良い。** 概念を分離できているということ。これが小さいモデルは「全部そこそこ似ている」としか言えない |
| **ハブ相関 r** | **0 に近いほど良い。** 0 から離れていると、類似度が意味ではなく**タグ本数**を測っている。ただし **\|r\| ≲ 0.1 はノイズ**（下記） |
| 群分離 | `None` や群サイズ 0 が出たら測定不能。`db-stats.mjs` で対照群の有無を先に確認する |
| 所要時間 | 重心算出が数十 ms で収まっているうちはキャッシュ不要 |

判断基準の実例（2026-07-30 / 解析済み1,008件）:

- `centering=false` では全ペアが 0.61〜0.99 に収まり **70.5% が1ビンに集中**した。
  絶対閾値でのゾーン分割は成立しない。**順位ベースが必須**という結論の根拠。
- ハブ相関は `centering=false` で **+0.337**、`true` で **+0.05 前後**。ハブ化は実在する。

**小さい r を読みすぎないこと。** 同じ `bge-m3` を対象メディア2件差で測り直したら、
r が **−0.097 → +0.035** と符号ごと動いた。標本は等間隔サンプリングなので、
母集団がわずかに変わるとどの個体を拾うかが総取り替えになる。
**\|r\| ≲ 0.1 は「ハブ化なし」以上の意味を持たない。** `+0.337` のような値は
この幅を大きく超えているので、そこは信用してよい。

### 実例（`similar_examples`）

**分布の数値が良くても結果が無意味ということはあり得る。** 必ず目視すること。
基準3件について、上位・中位・下位それぞれ3件をタグ名付きで出す。

見るべき点:

- **上位**が基準と意味的に繋がっているか。タグ文字列が一致していない組
  （例: 猫 ↔ うさぎ が「耳・ひげ・毛」で繋がる）が出れば、
  タグ完全一致では到達できない結果が得られている証拠になる
- **中位**が「無関係だが不快でない」か。ここがセレンディピティ枠になる
- **下位**が単に無関係なだけか（意味的な「反対」ではない。そう読めるラベルを付けてはいけない）

## 拡張するとき

- **条件を増やしたい** → `embedding.rs` の `measure_real_library` 内のループを触る。
  現在は `centering` × `include_descriptive` の4条件。
- **指標を増やしたい** → `EmbeddingDiagnostics` と `compute_diagnostics` に足す。
  設定画面の「類似度分布を計測」ボタンにも自動で乗る（同じ関数を通るため）。
- **基準メディアを指定したい** → `similar_examples` は現在、等間隔に3件を機械的に選んでいる。
  環境変数で media_id を渡せるようにするのが素直。
- **別アプリのDBを測りたい** → `--db` で任意のパスを渡せる。

## 対照群を人工的に作る

「解析設定の混在」がライブラリに存在しないと、群分離（`desc群内` / `群間`）は測れない。
実ライブラリは全メディアが descriptive を保有していることが多く、そのままでは対照群が無い。

`make-control-group.mjs` はスナップショットの一部から **descriptive タグの紐付けだけを外し**、
「descriptive 無しで解析されたメディア」を人工的に作る。

```bash
# ベクトル生成済みのスナップショットから作れば再生成が要らない
node tools/embedding-check/make-control-group.mjs --from tools/embedding-check/results/snapshot-bge-m3.db
node tools/embedding-check/run.mjs --db tools/embedding-check/results/control-group.db --models bge-m3 --only dist
```

**必ず `include_descriptive` の ON / OFF を両方見ること。** OFF が帰無条件になる。
OFF でも群が分かれて見えるなら、測っているのは descriptive ではなく別の何かである。

実測例（2026-07-30 / 506 対 502 / centering ON）:

| `include_descriptive` | desc 群内 | 非desc 群内 | 群間 | 差 |
|---|---|---|---|---|
| OFF（帰無条件） | −0.002 | 0.000 | −0.001 | 0.000 |
| ON | +0.025 | +0.026 | −0.028 | **0.053（0.38σ）** |

**これは模擬であって実データではない。** 紐付けを外したメディアの basic タグは
元の解析（DETAILED）由来のままなので、答えているのは
「descriptive の有無**だけ**で群が分かれるか」という一点に限られる。

### 分布が広いことは、それ自体では良い知らせではない

上の条件で descriptive を ON にすると sd は 0.132 → 0.141 と**広がる**。
しかしその広がりの中身は群分離そのものであり、意味的な分離ではない。
**sd だけを見てモデルや設定を選ぶと、この種の交絡を見落とす。** 群分離の指標と併せて読むこと。
